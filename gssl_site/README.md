# Green Spark Solutions Australia — Django site

The static design build in [`../green-spark-website/`](../green-spark-website/)
converted to a Django project. **The site is deliberately static**: every page
is a template with no database behind it. The admin panel and the content
models come next, and the structure here is arranged so that they can be
dropped in without rewriting templates.

The design build is **never modified**. It stays the source of truth for markup
and styling until the CMS replaces it, and the conversion is re-runnable.

---

## Quick start

```powershell
python -m venv ..\.venv
..\.venv\Scripts\python.exe -m pip install -r requirements.txt
..\.venv\Scripts\python.exe manage.py runserver
```

Then open <http://localhost:8000>. No database setup is needed to view the
site; `manage.py migrate` is only required if you want the Django admin login.

Run the checks:

```powershell
..\.venv\Scripts\python.exe manage.py test apps.website
```

```powershell
..\.venv\Scripts\python.exe tools\check_static_refs.py
```

## Layout

```
gssl_site/
  manage.py                     defaults to config.settings.dev
  requirements.txt
  .env.example                  copy to .env for local overrides

  config/
    settings/base.py            shared settings
    settings/dev.py             DEBUG, plain static files, console email
    settings/prod.py            HTTPS, HSTS, secure cookies, manifest static
    urls.py                     admin + website, handler404 / handler500
    wsgi.py  asgi.py            entry points (default to prod settings)

  apps/website/
    pages.py                    THE SITE MAP — one row per page
    urls.py                     generated from pages.py
    views.py                    one generic view for every static page
    context_processors.py       site_url, site_name, preview flag
    tests.py                    14 tests covering the conversion

  templates/
    base.html                   the whole document shell
    partials/                   the repeated blocks, one copy each
    pages/                      one template per page, content only

  static/                       GENERATED — copied from ../green-spark-website/assets
  staticfiles/                  GENERATED by collectstatic (gitignored)

  tools/
    convert_design_build.py     design build -> templates (re-runnable)
    check_static_refs.py        every /static/ reference resolves on disk
```

### Where to change things

| To change | Edit |
|---|---|
| Page text, markup | `templates/pages/<page>.html` |
| Header, footer, menus | `templates/partials/` |
| Stylesheets, scripts loaded on every page | `templates/base.html` |
| A page's title / description / share image | the `{% include "partials/page_meta.html" %}` line at the top of that page |
| Adding or moving a URL | `apps/website/pages.py` |
| The live domain | `DJANGO_SITE_URL` — never a template |
| Colours, spacing, type | `static/css/tokens.css` (see the design build README) |

## How the conversion works

The design build wraps every repeated block in
`<!-- partial:start NAME --> … <!-- partial:end NAME -->`, which made the
conversion mechanical rather than hand-copied.
`tools/convert_design_build.py` does it and **refuses to run** if the design
build disagrees with itself, so a silent mismatch cannot slip through:

1. Pulls each partial from all 24 pages and proves the copies are identical
   once active-state markers (`aria-current`, `is-current`) are removed.
2. Works out by byte offset which marker belongs to which nav item and emits
   one partial carrying a `{% if %}` at each varying position. A marker on
   *every* page is static and is kept as-is — that is how the mobile menu's
   `EN` language marker survives untouched.
3. Writes one page template per file, holding only that page's `<main>`.
4. Rewrites `../assets/…` to `{% static %}` and every `*.html` link to
   `{% url %}`.

Re-run it after any change to the design build:

```powershell
..\.venv\Scripts\python.exe tools\convert_design_build.py
```

It overwrites `templates/` and `static/`, so **do not hand-edit those while
you still intend to re-run it**. Once the design build is retired, delete the
script and the templates become the source of truth.

### What the conversion changed, and why

| Design build | Here | Why |
|---|---|---|
| Chrome repeated in all 24 pages | 11 partials, one copy each | ~2.4 MB of duplicated markup removed |
| `href="projects.html"` | `{% url 'website:projects' %}` | links survive a URL change |
| `href="../assets/…"` | `{% static '…' %}` | cache-busting hashes in production |
| `https://gssl.thingbd.com` hard-coded in every head | built from `SITE_URL` | the domain is set once, in config |
| `data-now="2026-11-25"` fixed | `{% now 'Y-m-d' %}` | event status stops being frozen in time |
| `class="is-preview "`, `social-links ` | tidied | stray whitespace in class attributes |
| `is-preview` + preview ribbon always on | `SHOW_PREVIEW_RIBBON`, off in production | the ribbon can't reach the live site |
| Social icon set inlined 3× per page | one `social_links.html` with a modifier | ~70 KB per page saved |
| Dangling `bootstrap-grid.min.css.map` reference | stripped from the `static/` copy only | `collectstatic` fails on it; browsers 404 on it |

Nothing else about the markup was touched. The design build's own choices —
no inline `<script>`, no `on*=` handlers, no `style=""` — were already correct
and are preserved, so the CSP in the design build README still applies.

## Next: the admin panel

`pages.py` is the hand-over point. Each row names a page; the rows with a
sample slug are the ones that become model-backed. The design build README
(§7 CMS field map, §8 loops) already specifies the models, and the loop
positions survive in the templates as `<!-- loop:start name -->` comments
marking exactly where each `{% for %}` goes.

The order that keeps the site working throughout:

1. Add models (`Programme`, `Project`, `Event`, `Post`, `Album`, `JobOpening`)
   plus a `SiteSettings` singleton for contact details and social links.
2. Move the hard-coded values out of `context_processors.site()` — the
   template variables keep their names, so no template changes.
3. Convert one listing page at a time: replace the markup inside a
   `loop:start` comment with a `{% for %}` over the queryset.
4. Collapse the six programme templates into one slug-driven view.
5. Retire `tools/convert_design_build.py` and the design build.

## Deployment

Production settings require these environment variables, and refuse to start
without the first two:

| Variable | Example |
|---|---|
| `DJANGO_SECRET_KEY` | `python -c "import secrets; print(secrets.token_urlsafe(64))"` |
| `DJANGO_ALLOWED_HOSTS` | `greensparksolutions.com,www.greensparksolutions.com` |
| `DJANGO_SITE_URL` | `https://greensparksolutions.com` |
| `DJANGO_BEHIND_PROXY` | `1` when nginx/Apache terminates TLS |

```bash
export DJANGO_SETTINGS_MODULE=config.settings.prod
python manage.py migrate
python manage.py collectstatic --noinput
gunicorn config.wsgi:application --bind 0.0.0.0:8000
```

Static files are served by WhiteNoise with hashed filenames, so no separate
static host is needed; put nginx in front for TLS and compression.

**Before going live**, work through §11 of the design build README — the
sample data (impact counters, event dates, Gold Standard IDs, team names)
still needs GSSL's sign-off, and `tools/self-host-photos.py` should be run so
no photo loads from a third-party server.
